# OTA end-to-end checks

Run `python3 -I tools/validation/Update/run_e2e.py --host <test-pc> --expected-machine <COMPUTERNAME> --feed-url https://<feed-host>:8460/ota-e2e/beta.json --signing-key <private-key.pem> --scenario all` from this worktree. The only Windows target is `<test-pc>` / `<COMPUTERNAME>`. The runner stages a fresh protected source frame, builds the source App.Version and a temporary copy with the next patch version and same prerelease suffix, serves signed releases through tailnet HTTPS port 8460, and drives the installed app through UIAutomation. It leaves the source version installed with the test feed and stops its own processes. It never publishes to Vercel or copies the signing key to Windows.

Each named scenario records installed DisplayVersion, the running executable's product version, Settings and banner text, update-folder files/hashes, process-start events, saved-rule/settings/undo hashes, and screenshots under `artifacts/ota-e2e/`. The derived versions and installer URLs stay fixed while each refusal case varies its named input. The pair builder requires `-VersionA` and `-VersionB`; the Python runner supplies them and passes the same versions to the contract and desktop checks.

Failure cases recorded before implementation:

- Unreachable, slow, redirected-to-HTTP, malformed, non-200 or oversized feeds must finish with a visible refusal without blocking navigation.
- Invalid envelope/schema/key/base64/signature or payload/product/channel/version/URL/size/hash must never reach download or execution.
- Equal, older, or prerelease versions with lower SemVer precedence must not download.
- Automatic download off must require Download; repeated checks/clicks must not overlap.
- Truncated, oversized or changed installer bytes must remove partials and never start setup.
- A changed ready installer or mismatched product version must fail a locked-handle recheck before execution.
- An active game session or timer must prevent installation, including a session started during the confirmation dialog.
- A canceled confirmation must not start setup or write a pending installation.
- Silent setup must exit and relaunch on success and on a failure before file replacement, without waiting for a prompt.
- Upgrades must preserve settings, rules, undo data and governor enabled/running state.
- Update storage must deny non-administrator writes, links and untrusted paths; runtime settings cannot choose a feed or executable.
- Cleanup must affect only this runner's frame, tasks, PIDs and tailnet port 8460.
- A failed copy after InstallDelete can remove the old executable; silent setup must then open the same installer interactively so it can complete recovery. The copy-failure fixture creates a directory at the executable destination only in silent mode, after deletion and three copied files while the app executable is still missing. The ensuing file write fails. Its interactive recovery uses the same payload without that failure. A script exception alone was insufficient: Inno logged it and continued copying under the silent switches.
- Install-drive free space must reject 1 GiB minus one byte and accept exactly 1 GiB. The probe records the real install drive and available bytes, then varies only the free-byte input to the same comparison used by InstallAsync. Filling a shared PC's system drive is avoided.
- Publication Boolean switches must agree with the actual Vercel 59.3.0 parser: immutable installer defaults false/false; the manifest alone supplies bare allow-overwrite. The parser check evaluates the bundled parser locally and never uploads.

The pure contract probe consumes real signed manifests and streamed installer files; the desktop cases exercise the installed release app and installer. Neither uses a production endpoint.

`scheduled-download` waits for the startup check without pressing Check. `slow-feed` uses the standard library HTTP fixture to delay the same feed body for 25 seconds; the normal scenarios use `python3 -m http.server`. Equal/older and wrong-product/channel manifests change only their named payload field and are re-signed on Linux. `tampered-size` appends one byte to exercise the hard cap, while `tampered` flips one byte without changing size.

To resume a journey, keep its unchanged verified frame, then pass `--receipt`, `--build-root`, `--evidence-root`, `--skip-build` and `--from-scenario <name>` to the runner. Keep the original nonce-bound seed results in the frame ledger; they are frozen baseline data. The first manual upgrade proof remains in `manual-0.10-to-A`, and the later reset uses `reset-A`.

After copying evidence, clean each owned staging/build frame by passing its exact path to `Clear-UpdateFrame.ps1` through `windows_ssh.py run`. It accepts only this OTA runner's prefixes and refuses live processes and linked entries. The installed app, saved rule/theme and undo data remain; cleanup removes only caches recorded as created by the run.

The runner requires `--host`, `--expected-machine`, `--feed-url` and `--signing-key`, or `ROO_TEST_SSH_HOST`, `ROO_TEST_COMPUTER`, `ROO_TEST_UPDATE_FEED` and `ROO_UPDATE_SIGNING_KEY`. There are no private infrastructure defaults. `serve_fixture.py --fault http-error|disconnect|stall-installer` varies only installer transport; the stall exercises the real twenty-minute download deadline. The timer-read fixture uses a separate app copy and a temporary Core source copy whose `TimerControl.Read` throws unconditionally. The installed app clears test environment variables, so an environment switch cannot force this check. The scenario requires the exact warning in the new app-log text; release Core and installed files stay unchanged.

## Published release journey

`run_shipped.py` runs the published installer against real desktop sessions. Required `--source-commit` selects the source commit; the product diff and working-tree status under `backend`, `docs`, `tools/release`, `tools/scripts`, `assets` and root build properties/targets must be empty. P0 and P2–P5 require `--published-installer`: Linux verifies the feed signature against `update-keys.json` and requires its installer size/SHA-256 to match that local file. The verified version comes from the payload. P2 also requires `--baseline-installer` and `--baseline-sha256` and refuses a mismatch. Hostnames and signing-key paths come from arguments or existing environment variables, with no private defaults. The feed URL comes from `tools/release/update-feed.txt`. Production access is GET-only; the runner never publishes. Every invocation fetches and verifies the live feed. Cached payload hashes are bound to the installer SHA-256.

Run parts in order on one PC, with a separate reachable CCD test PC allowed in parallel with P1:

```text
python3 -I tools/validation/Update/run_shipped.py --scenario p0 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --blackwell-host <ccd-test-pc> --blackwell-machine <CCD-COMPUTERNAME> --published-installer <published-installer.exe> --out-dir <evidence-folder>
python3 -I tools/validation/Update/run_shipped.py --scenario p1 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --test-feed-url https://<feed-host>:8460/ota-e2e/beta.json --signing-key <private-key.pem> --out-dir <evidence-folder>
python3 -I tools/validation/Update/run_shipped.py --scenario p2 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --baseline-installer <baseline-installer.exe> --baseline-sha256 <64-hex> --published-installer <published-installer.exe> --innoextract <innoextract-binary> --out-dir <evidence-folder>
python3 -I tools/validation/Update/run_shipped.py --scenario p3 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --published-installer <published-installer.exe> --innoextract <innoextract-binary> --out-dir <evidence-folder>
python3 -I tools/validation/Update/run_shipped.py --scenario p4 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --published-installer <published-installer.exe> --out-dir <evidence-folder>
python3 -I tools/validation/Update/run_shipped.py --scenario p5 --source-commit <release-commit> --host <test-pc> --expected-machine <COMPUTERNAME> --blackwell-host <ccd-test-pc> --blackwell-machine <CCD-COMPUTERNAME> --published-installer <published-installer.exe> --innoextract <innoextract-binary> --out-dir <evidence-folder>
```

P0 preserves installed versions, data hashes, task XML and Tailscale configuration. P1 runs the existing full suite, contracts, both transport faults, read-only settings, the timer fixture and the real twenty-minute manual-download timeout on one source receipt. P2 uninstalls the current build, seeds the hash-verified baseline release, leaves its app/governor running, downloads the published installer once on Windows, adds browser MOTW, and drives the normal wizard with unchanged default choices. Its payload comparison uses `innoextract`, independently of the source build. A fixture launched through the verified desktop Explorer dispatch must begin with CPU, affinity and memory values all different from the saved High/0x3/memory-2 rule, then reach all three targets. P3 builds a temporary copy changing only App.Version to the same release core with an alpha prerelease, verifies the embedded production feed, then runs the live startup download and silent upgrade to the signed beta payload. P4 uses a named outbound firewall rule for the installed app only and removes it after the navigation check. P5 independently asserts background fixture masks against live CCD topology, unchanged game/protected masks and every restored original value; it also checks guides/minimized private working set and uninstalls if absent before the run. Do not power on an unreachable PC.

Failure ways recorded before P2–P5 execution:

- P2: a wrong local 0.10 hash; stale/tampered live feed; repeated installer GETs; missing browser MOTW; SmartScreen (evidence and failure) or an unhandled wizard/UAC dialog; non-default close/Finish choices; an old app or governor retaining files; setup success with wrong installed bytes/version; mutated settings/rules/undo files; governor pointing at old bytes; a newly launched game missing any saved field; cached status masquerading as a live check; unexpected download; exceptions or setup errors.
- P3: source changes beyond Version; a test feed accidentally embedded; alpha not lower by SemVer; installer refusing alpha; preservation loss during alpha install; an overlapping/manual check replacing the startup check; transport/content mismatch; unverified bytes or wrong ProductVersion executed; lost pending record; setup not receiving wait/relaunch arguments; old app surviving; no relaunch/banner; governor/data loss; leftover installed cache; a later Check failing to reach Current.
- P4: blocking a helper or other app instead of the installed app; a cached Current result hiding failure; an unbounded check; blocked navigation; failure to remove the exact rule; restored networking still failing; cleanup killing another PID.
- P5: unreachable SSH mistaken for powered-off hardware; changing unrelated tasks or old frames; installing different bytes; no live check; a full/wrong CCD mask or wrong logical count; protected/game fixtures changed; Restore missing originals; guides failing to render; substituting private bytes for private working set; leaving any Suite task/service/files/data after a fresh-install check; stopping a process that existed before the run.

Receipts, process-start records, exact Settings text, wizard/UI screenshots and logs are collected under the selected evidence folder. The Inno default leaves “Open” unchecked; the harness preserves that choice and launches the app afterward. The published 0.11.0-beta update log records status reasons but has no feed-host/key-ID logging; the receipt labels those absent log fields as unverified and keeps signature/resource evidence separate. Product failures stop the part and keep its evidence. Harness repairs must be labeled and may not change product source. After collecting evidence, remove only the runner's exact frames with `Clear-UpdateFrame.ps1`, remove only its port 8460 entry, and audit the as-found task/Tailscale state.

The browser download uses a unique folder under the signed-in user's Downloads folder. The harness starts a separate owned PowerShell launcher, which calls ShellExecute, records the setup immediately and writes a nonce-bound CreateNew result. The harness handles only that launcher's Open File security warning and its setup descendants. Native security-warning buttons can expose a Pane instead of Invoke; the driver sends the named button's command only to its verified same-process parent. Guide headers use ExpandCollapse. App attachment waits for the window containing Settings rather than an empty startup window. Screenshots temporarily raise their exact window without moving or resizing it, then restore its original topmost state so a launcher console cannot cover the evidence.

Preserve interrupted evidence before starting a fresh shipped run; P1 alone supports `--p1-from-scenario <name>` and `--p1-extras-from <name>` on its recorded receipt, with `run_e2e.py --scenario-script <relative-script>` for an explicitly recorded helper copy.

The tester journey proves the governor running during upgrades. Final cleanup must then pause that owned governor through `Invoke-ProcessPolicyWorker.ps1 -Action Pause -ConfirmApply`; stopping its Host alone would let the repeating task restart it. Preserve rules, settings and undo files, and record this deliberate final pause separately from the upgrade results.

Run `Collect-RestartEvidence.ps1` through `windows_ssh.py interactive` on a verified frame, with `-OutRoot <fresh-evidence-folder> -ExpectedMachine <COMPUTERNAME> -StartUtc <ISO-UTC> -EndUtc <ISO-UTC>`. It reads a bounded log window without changing auditing, event-log configuration or product state, and saves both data-root app logs, UTC-converted lines and whole-log restart matches; full System messages/XML; Security process starts and available shutdown-parent records; task, SSH and PowerShell events; current auditing policy and retention bounds. Missing/disabled/expired evidence cannot rule a cause out.

Owned-process chains, fresh log cursors (including one rotation), installer identity and the exact local source manifest bind every reused frame. A foreign app, setup, fixture, firewall rule or data root is retained and refused. P4 also tests navigation during an owned hosts-file timeout and removes only its nonce-marked entry. Receipt status is finalized after cleanup; cleanup failures fail the run. Download totals count completed installer downloads.

## Logging and test signatures

The update runner checks fresh host-only feed logs for Current, Available, refused signatures and HTTP 502, alongside the unchanged Settings text. It rejects a feed path or query in that log segment.

`Invoke-SigningScenario.ps1 -Source <frame-source> -OutRoot <owned-frame-folder> -Scenario build -FeedUrl <test-feed> -VersionA <source-version> -VersionB <next-version>` creates a two-day test signing certificate in CurrentUser\My, obtains an owned SDK signtool package only if needed, and builds signed A/B installers. It exports no private key and changes no root trust. Use `start-governor` before the signed journey's `seed`; then run `manual-install`, `ready` and `install` with the update runner on the same receipt/build paths. `verify-A` and `verify-B` read every installed Roo Industries signature, the uninstaller, both setups and the running governor without starting a replacement worker. `negative` proves a wrong subject fails before ISCC. Run the update `cleanup`, then signing `cleanup` to pause the governor and delete only the recorded test certificate. Copy evidence before removing the owned frame and SDK package.
Every Update harness uses `Harness.Common.ps1` and the frame's creation ledger. Each invocation has a random nonce; result filenames and contents carry it, use CreateNew, and readers verify its ledger identity and hash. Cleanup walks only recorded creations in reverse and retains any identity mismatch. P5 snapshots both data roots, the install directory and tasks at its own start; P0 is informational. Cache preflight rejects foreign source/next-version folders, and reset removes only the run's actual next version. Frame reuse requires the exact full source file set and hashes; staging scans all file contents for private-key material before SSH.

SmartScreen stops the harness with a screenshot and UIA tree: a tester presses More info -> Run anyway.

`python3 -I tools/validation/Update/run_harness_checks.py --host <test-pc> --expected-machine <COMPUTERNAME> --source-commit <published-source-commit> --published-installer <published-setup.exe> --out-dir <fresh-artifact-folder>` runs the owned fixtures, including a live runner started through the real `windows_ssh.py interactive` path. `contracts --skip-contracts` is invalid. The hanging-network check requires the exact request-timeout status 18 to 30 seconds after Check; hosts cleanup holds one exclusive stream across read, truncate and write. Pre-existing install logs are preserved; Current/no-download checks require a fresh log segment from the owned app and no release cache.

`close-during-check` serves a slow test feed, closes only the owned app while Settings says Checking for updates, and requires the host-only closing-cancellation log plus exit code zero. Contract probes check verified key IDs on signed payload refusals; ready recovery checks the Cached feed line. User-visible status text remains unchanged.

`ready` primes a verified next-version cache, closes its owned app and launches it again so cached-feed recovery is measured from the new process. The ledger retires a cache identity when the app has removed that directory. `Invoke-HarnessChecks.ps1 -CacheOnly` checks cache identity retirement, and `-TimeoutOnly` checks the exact hanging-request status and 18/30-second boundaries; it does not replace the real P4b request.

The shared process-start trace subscribes to Win32_ProcessStartTrace before product launches. A separate .NET event callback buffers events during UI or ledger locks. Trace adoption requires a recorded owned-parent chain, invocation timestamps in order, exactly one event for the PID between one second before and ten seconds after native birth, and the same retained native handle. The receipt records lagMs. Live parent proof is also accepted; paths and titles only locate candidates. SmartScreen is never clicked.

`Invoke-TraceOwnershipChecks.ps1` covers a 25 ms parent under an 800 ms ledger lock, the same image under a foreign parent, and simulated PID reuse. The foreign fixture belongs to its own ledger; child fixtures self-exit after 120 seconds if a proof fails. `Invoke-HarnessChecks.ps1 -TrackingOnly` runs the three ownership checks and an ambiguous-birth check. The existing forty checks remain available through `run_harness_checks.py`.

SSH/SCP use direct bounded connections without shared ControlMaster sockets, connection/keepalive limits, and subprocess deadlines (75 seconds for commands, 300 seconds for transfers; desktop scenarios retain their requested bounded deadline). `python3 -I tools/validation/Update/check_windows_transport.py --host 192.0.2.1 --expected-machine UNREACHABLE --out-dir <new-output-folder>` verifies real SSH/SCP refusals under 90 seconds on Linux.

Add `--live-host <test-pc> --expected-machine <computer-name>` to check a live 20-second command with a five-second deadline and an immediate follow-up. RemoteTimeout is a run failure; only exit-255 connection errors are HostUnreachable. Source verification/extraction allows 300 seconds, evidence archives 600 seconds, and frame cleanup 900 seconds. `windows_ssh.py run --timeout <seconds> <script>` supplies an explicit bound for longer direct scripts.

Use a short `-OutRoot <frame>\s` for `Invoke-SigningScenario.ps1`. Its preflight refuses an intermediate XAML assembly path of 260 characters or more before creating a certificate. The Windows XAML compiler cannot resolve that assembly through a long ordinary path. Certificate cleanup reads its creation ledger even when the build failed.

The harness uses one extended-path tree walker and file-hash helper for source, data, cleanup and ZIP evidence. Run `python3 -I tools/validation/Update/run_harness_checks.py --lint-only` before staging; the driver enforces the same lint before Windows checks.

Update drivers use `upload_frame` / `interactive_frame` and hold a ledger-owned `C:\RooBuild\host-lease.json` until frame cleanup; legacy transport entry points retain the v1 invocation contract. `run_harness_checks.py --frozen-p0 <snapshot-folder>` overrides the repository-wide frozen inputs; `--resolve-inputs-only` checks resolution without contacting a PC.

`cache-cleanup` holds an owned installed-version cache file for 5 and 40 seconds from the native app birth, then checks deletion within 35 seconds, the single terminal warning, continued app operation and next-start retry. The all journey includes it after same-version. Install/copy-failure read back cache absence within 35 seconds; ready checks an owned older cache is removed while the newer installer and creation identity stay unchanged.

For an unpublished release candidate, `run_shipped.py --scenario p2 --candidate --source-commit <release-head> --published-installer <candidate.exe> --baseline-installer <real-0.10.exe> --baseline-sha256 <baseline-sha> --host <test-pc> --expected-machine <computer-name> --innoextract <binary> --out-dir <fresh-folder>` stages local candidate bytes with MOTW and verifies the live signed feed independently. It never requests an unpublished URL. SmartScreen is recorded and never clicked; the owned launch is canceled before a labeled retry without MOTW. `--scenario p2b --candidate` uses the published prior installer as its baseline and emulates only the pending record, deliberate child environment, silent setup arguments and clean app close. Its trace-bound relaunch, payload, preservation, governor and cache checks do not claim feed-driven OTA before publication.

`Build-ReleaseCandidate.ps1 -Source <staged-source> -OutRoot <frame-child>` builds unsigned with the exact committed feed, runs the release smoke test, reads the embedded resource and records the installer identity plus every payload hash. `-ProbeOnly` builds the same invocation-bound installer-launch probe for P2b.
