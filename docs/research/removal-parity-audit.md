# Removal and cleanup parity audit

Checked **2026-09-16**. The requested core is multi-app vendor removal followed by reviewed, recoverable app-specific file and registry cleanup. That path has Windows fixture evidence. This audit found and repaired a loss of shared ownership information after multiple removals. Complete Revo parity or superior discovery has not been established.

Revo Free documents vendor uninstall followed by file, folder and registry scanning. Revo Pro documents consecutive multi-app removal and warns that shared installation folders can produce another product's leftovers. These are the relevant comparison behaviors; the number of deleted entries alone is not a quality measure. [Free features](https://www.revouninstaller.com/products/revo-uninstaller-free/), [Pro uninstaller manual](https://www.revouninstaller.com/online-manual/uninstaller/).

## Removed-app ownership repair

Before the repair, [Host `CleanupContextFor`](../../backend/native/Optimizer.Host/Program.cs) constructed `Peers` exclusively from current installed inventory. Other apps removed by the same queue disappeared from that inventory, losing their saved ownership evidence. If app B's files sat beneath app A's install folder, selecting only A's leftovers could incorrectly offer B's data for deletion. Registry ownership had the same dependency. Batch overlap checks did not protect an app omitted from cleanup selection.

The Host now combines fresh inventory with all saved queue snapshots. Distinct metadata claims are retained even if they share an app ID; current registration absence does not erase an earlier ownership claim. Missing snapshots or snapshot/entry identity mismatches reject discovery.

The expanded [Host regression](../../backend/scripts/Test-OptimizerHost.ps1) installs two disposable registrations with nested paths and a registry reference, runs both fixture removers through the production queue, independently confirms both are absent, and scans only the first app. The old implementation failed the nested-owner assertion. The repaired version retains the second owner on both folder and whole-key candidates, rejects explicit previews for those shared resources, and preserves the independently specified file and registry contents. Separate mutations prove that missing and mismatched peer snapshots are rejected. The existing disjoint-app deletion/restoration test and native application cleanup checks also passed.

## Discovery scope and remaining comparison evidence

- **Files:** published install locations, exact package-family data, and name-matched directories in Local, Roaming, LocalLow, ProgramData and both Program Files roots. Searches descend one extra level under a matching publisher or `Programs`; they do not discover arbitrary drive locations, every loose file or every shortcut. See [root selection and folder traversal](../../backend/native/Optimizer.Core/LeftoverDiscovery.cs).
- **Registry:** current-user Software, the redirected user Classes view and both machine Software views. Matching uses product key names and string references to the installation path; it is not a complete dependency graph. Depth is capped at 64 and visits at one million keys. Failures remain visible and incomplete candidate subtrees cannot be approved. See [registry traversal](../../backend/native/Optimizer.Core/LeftoverDiscovery.cs).
- **Execution:** protected/shared locations and unsupported file storage forms remain excluded. Whole-key recovery preserves captured data and ordinary security metadata with documented recreation limits. [Control and cleanup limits](../optimization-controls.md#control-and-cleanup-limits) define these boundaries.
- **Comparison:** no matched, labeled real-application corpus was run through both products. Discovery recall, false positives, scan cost and practical MSI/Appx coverage remain unmeasured. The fixture suite supports functional readiness, not a claim of removing more safely than Revo.
