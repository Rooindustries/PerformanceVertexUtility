# Registry cleanup and recovery contracts

Checked: **2026-09-15**. This extends [the uninstall research](uninstall-cleanup.md) with the native registry boundary. It specifies proposed behavior and required Windows checks; it does not report registry execution or machine testing.

The useful implementation target is selective cleanup of reviewed app-owned keys and values, backed by exact value data, explicit security coverage, transaction results, and conflict-aware recovery. A registry name match is discovery evidence. It is not ownership or deletion authority. Vendor uninstall, registry cleanup, and restoration of cleanup data remain separate operations.

## Decision table

The following decisions precede fixture construction. They combine the existing uninstall contract with the Windows API contracts below. All required signals are independent; a favorable queue status does not override an unavailable provider, pending reboot, changed resource, or conflicting owner.

| State and required evidence | Binding and permitted transition | Expected result |
| --- | --- | --- |
| Completed removal; exact provider registration absent; provider query complete; no pending reboot or unresolved remover result | Same machine, owner SID, provider identity, queue entry, and reviewed resource set | Eligible for a fresh registry preview, subject to resource ownership and recovery coverage. Absence alone grants no cleanup authority. |
| Queue says removed, but registration is present again | Preserve the reviewed app identity even if its display name or version is similar | Stop cleanup and restore for that app; require reconciliation with the current installation. Never delete the returning registration to make the old review valid. |
| Queue says removed, but provider query failed, was partial, or omitted scope | Unknown state remains unknown | No destructive transition. Report the failing provider/API and status. |
| Removal accepted but reboot pending, remover still active, timed out, or result missing | Independent reversing/blocking signals remain authoritative | Wait for reconciliation. Do not infer completion from a missing process or zero remaining scan results. |
| Exact key or value lookup returns not-found in a verified accessible parent and the correct scope | Match hive, view, SID, native key name, and explicit value name | Record already absent. Do not invent deleted counts or recreate it merely to run cleanup. |
| Lookup returns access denied, invalid/deleted handle, resource-manager failure, or another error | Preserve the actual API error | Record inaccessible, changed, or unavailable. Never collapse these states into absent. |
| Resource snapshot, owner evidence, and approved security coverage match; backup is durable and verified | Preview digest, app identity, operation ID, exact resource identity, backup digest | Revalidate inside a short transaction, stage only the reviewed mutations, then commit and verify. |
| Value name is unchanged but its type, byte length, or data changed | Raw bytes and numeric type are independent signals | Invalidate review. Equal display text is insufficient. |
| Key gained/lost children or values; class/security/last-write evidence changed | A key review covers an exact subtree, not an expandable pathname | Invalidate that key review. A reviewed value can remain separate from unrelated siblings if its parent identity and policy still hold. |
| A key was deleted and recreated at the same path | Names and timestamps are not unique object IDs | Treat detected replacement as stale. Persisted snapshots cannot promise detection of every identical-content replacement. Retained apply handles prevent a later lookup from silently selecting another object. |
| Link, unexpected native destination, merged/virtualized scope, shared owner, or unsupported metadata appears | Exclusions override matching names and manual selection | Keep detection available; do not mutate that candidate under an unsupported contract. |
| Another writer changes a participating key; transaction fails, times out, or reports conflict | A staged delete is not a committed result | Roll back, preserve backup and actual outcome, and require a fresh snapshot before retry. Do not switch silently to nontransacted deletion. |
| Process exits after commit intent but before journal completion | File journal and registry transaction are separate resources | Reconcile a transaction receipt and actual registry state. A missing key alone does not prove this operation deleted it. |
| Restore target absent, parent verified, app still absent, backup valid | Same operation, exact destination, captured type/data/security coverage | Create only reviewed missing keys or values inside a new transaction; verify before and after commit. |
| Restore destination exists and equals the complete recorded restore result | Require durable operation evidence, not just one matching value | Report already restored without rewriting it. |
| Restore destination exists and differs, has new children, changed security, or has another owner | New state overrides old recovery intent | Report conflict without overwrite or deletion of new state. Partial recovery is itemized. |
| Backup corrupt, path/digest/app mismatched, required security unavailable, or registry transaction unavailable | Do not invent defaults for missing metadata | Refuse that mutation with its precise requirement. Other independently supported items remain usable. |
| Original key persistence is unknown; the review explicitly selects persistent recreation with defined data/security coverage | Bind this recovery policy and its limitations to every selected key, review digest, backup, and journal | Whole-key cleanup may proceed when the selected coverage is complete and the other eligibility checks pass. Restoration deliberately creates persistent keys; it does not report the original keys as nonvolatile. |

## Identity, scope, and views

Bind a resource as `(machine, hive, ownerSid, requestedView, nativeKeyName, kind, valueName)`. `kind` distinguishes a key from a value; `valueName: ""` means the unnamed value, while an omitted value name is invalid for a value operation. Preserve the logical path for display and the queried native name for verification. Use case-insensitive identity comparison without lowercasing raw value bytes.

WOW64 flags select views, but shared keys ignore them. Child opens/creates/deletes must explicitly retain the selected flag. Do not construct `Wow6432Node` paths: Microsoft reserves those paths for compatibility. [Alternate registry views](https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view).

On current Windows, `HKLM\Software` is redirected, while ordinary `HKCU\Software` is shared. Some `HKCU\Software\Classes` descendants, including `CLSID`, are redirected. The same physical resource can therefore appear twice when enumerating both views. Deduplicate a verified native destination and value name while retaining its discovery aliases. Do not merge genuinely different view destinations. [WOW64 key map](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys).

The cached `HKEY_CURRENT_USER` mapping is unsuitable for a helper that changes impersonation context. `RegOpenCurrentUser` uses the thread token and may use a default profile when the user's profile is not loaded. Bind the requested SID, verify the resulting native root, and refuse a mismatched/default root. Do not load another user's hive as an incidental cleanup step. [RegOpenCurrentUser](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopencurrentuser).

`HKEY_CLASSES_ROOT` is a merged view, so mutation should address the explicit underlying user or machine key. Legacy virtualization can also merge user and global data; it is disabled for 64-bit processes and processes with `requestedExecutionLevel` in their manifests. Package the helper accordingly and identify VirtualStore candidates separately. [Merged classes view](https://learn.microsoft.com/en-us/windows/win32/sysinfo/merged-view-of-hkey-classes-root), [registry virtualization](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-virtualization).

## Snapshot and recovery fidelity

Use `RegQueryValueExW` into byte buffers. Persist numeric type, returned byte count, and exact bytes; keep any decoded text as display-only data. An unnamed value may be missing or may have any type. `ERROR_FILE_NOT_FOUND` is different from a successful zero-byte read. Retry `ERROR_MORE_DATA` with bounded allocation, never using its undefined partial buffer. [RegQueryValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw).

Cover `REG_NONE`, binary, little- and big-endian DWORD, QWORD, string, expandable string, and multi-string distinctly. Preserve literal environment tokens and embedded zeroes. Registry strings can already be malformed; never normalize the backup. However, `RegSetValueExW` requires the documented string terminators. A successful raw reader alone does not establish a supported writer for malformed or unknown types. Keep those candidates read-only until an explicit recovery contract is implemented and verified. [Registry value types](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-value-types), [RegSetValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetvalueexw).

Enumerate complete names and children before constructing the review. Enumeration order is arbitrary; sort only the canonical snapshot. Reset buffer capacities on every call, distinguish end-of-enumeration from failure, and bound key count, depth, value length, and total bytes. Truncation makes a key snapshot incomplete, not safe to delete. [RegEnumValueW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumvaluew), [RegEnumKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumkeyexw).

`RegQueryInfoKeyW` provides class, counts, sizes, and last-write time. The timestamp describes changes to that key or its values, not a unique key identity or a recursive subtree hash. A parent timestamp cannot replace inspection of every descendant. Store it as additional freshness evidence. Neither this contract nor `KEY_NAME_INFORMATION` establishes a durable object ID, so restored keys must not be described as the original key objects. [RegQueryInfoKeyW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw).

For key deletion, record the security components actually captured. Owner/group/DACL require `READ_CONTROL`; SACL access requires the security privilege and `ACCESS_SYSTEM_SECURITY`. A missing SACL field means uncaptured, not empty. Keep the binary descriptor and its coverage mask; a display SDDL string is not the sole backup. [RegGetKeySecurity](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-reggetkeysecurity).

Restoration must account for owner, group, DACL, SACL/labels where covered, and inheritance/protection flags. Those are separate `SECURITY_INFORMATION` components. Apply descriptors through the restored key handle and read them back. Never claim full security restoration from a DACL-only check. Value-only deletion leaves the parent key and its security intact; whole-key deletion needs a stronger recovery contract. [SECURITY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-information), [RegSetKeySecurity](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetkeysecurity).

Suggested explicit coverage fields are `rawValues`, `class`, `ownerGroupDacl`, `sacl`, `inheritanceFlags`, `keyPersistence`, and `lastWriteTime`. Mark each captured, unsupported, or not applicable. Recreating a key does not restore its prior last-write time or prove its original volatile/nonvolatile mode. Uncaptured properties must not receive reassuring defaults. Require adequate coverage for the selected operation before deletion.

`RegSaveKey` is a hive-format backup option, not a selective default: it omits volatile keys, requires `SeBackupPrivilege`, and can leave a corrupt file after failure. `RegRestoreKey` overwrites destination contents, has open-handle restrictions, and requires backup/restore privileges. Do not use force-restore or hive replacement to implement ordinary missing-item recovery. [RegSaveKeyW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsavekeyw), [RegRestoreKeyW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regrestorekeyw).

## Explicit persistent-key recovery

**Recommendation:** support whole-key deletion with an explicitly selected recovery policy that restores supported raw values plus captured owner, group, and DACL, while recreating keys as ordinary persistent keys. This is a functional data-and-captured-permissions contract. Unknown original persistence is not a reason to disable that deliberately bounded mode, and it must not be converted into a claim that the source was nonvolatile.

Use separate fields such as `originalPersistence: "unknown"`, `restorePersistence: "nonvolatile"`, and a versioned `recoveryPolicy`. Bind the policy to the approved review and backup. An old review without the field does not authorize the new behavior. Selection of whole-key deletion should show the recovery scope before apply; value-only cleanup remains available without key recreation.

Suggested review wording:

> Restore saved data and captured owner, group, and DACL. Removed keys will be recreated as persistent keys. Original persistence, timestamps, and uncaptured audit or integrity settings are not restored.

The distinction has an actual effect: `REG_OPTION_NON_VOLATILE` stores new keys for subsequent restarts; `REG_OPTION_VOLATILE` has a different lifetime. The creation option does not convert an already-existing key, so restore must check the creation disposition and reject conflicting existing destinations. [Key creation options](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeyexw).

Do not describe owner/group/DACL coverage as complete Windows security restoration. If SACL, integrity labels, class, or another property was not captured or is excluded by this policy, show that coverage separately. The policy does not waive ownership, link, integrity, backup, or conflicting-writer checks. Missing required raw data or a promised DACL remains a failure.

Value-only cleanup preserves the existing key object, persistence mode, class, and security descriptor by leaving the key itself in place. It still changes the key's last-write time when a value changes, so “all metadata unchanged” would be incorrect. [Last-write time contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw).

Revo's manual documents deleted-registry-item backups and selective restoration, alongside separate full-registry backup options. The reviewed pages do not specify timestamp, volatility, or security-descriptor fidelity for selective restore. They establish the comparable workflow, not proof that Revo restores those properties or omits them. The replacement should state its stronger, testable details directly. [Revo Backup Manager](https://www.revouninstaller.com/online-manual/backup-manager/), [Revo backup options](https://www.revouninstaller.com/online-manual/options/).

## Links and retained handles

`REG_OPTION_OPEN_LINK` opens a link source rather than its destination. Inspect one path component at a time, including ancestors, and reject unsupported links or `REG_LINK` values. A normal open can follow a link. Merely checking a path and reopening it later leaves a replacement window. [RegOpenKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw), [BaseRegOpenKey contract](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/8cb48f55-19e1-4ea2-8d76-dd0f6934f0d9).

`RegOpenKeyTransactedW` requires `ulOptions=0`; passing `REG_OPTION_OPEN_LINK` there is outside its documented contract. Subkey operations do not automatically join a parent transaction. Consequently, opening a child with `RegOpenKeyEx(OPEN_LINK)` under a transacted parent is not documented proof that the returned handle participates in that transaction. [RegOpenKeyTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeytransactedw).

`NtQueryKey(handle, KeyNameInformation, ...)` can inspect the actual opened key without reopening its path. Microsoft explicitly names `NtQueryKey` for user-mode callers. `KEY_NAME_INFORMATION` contains a byte length and a non-NUL-terminated wide-character name. Bounds-check both lengths; do not marshal it as an arbitrary terminated string. [Query-key API](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwquerykey), [name structure](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_key_name_information).

**Implementation inference requiring Windows fixtures:** after each transacted open, compare that handle's native name against the reviewed destination before reading or writing values. Retain it for mutation. A followed link to a different destination then fails the comparison. Establish expected native roots with verified handles rather than trusting user-supplied native names. Verify children separately; checking only the root does not validate a tree. This is a destination check, not a globally unique identity or a lock against every future rename/recreation.

The driver-level `ZwOpenKeyTransactedEx` contract supports `REG_OPTION_OPEN_LINK`, but documents a kernel DDI. It does not justify silently substituting an undocumented user-mode export or installing a driver. `KeyFlagsInformation` and `KeyHandleTagsInformation` are reserved for system use. Ordinary cleanup should not depend on them. [Transacted open DDI](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwopenkeytransactedex), [key-information classes](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_key_information_class).

## Transaction and commit contract

Microsoft continues to document KTM and Transactional Registry APIs, with Windows Vista as the minimum client. The reviewed TxR pages contain no retirement notice. This establishes a documented API surface, not availability on a particular Windows 11 installation; probe creation, rollback, commit, and conflict behavior in disposable keys. Do not transfer Transactional NTFS guidance to TxR without a registry-specific source. [KTM](https://learn.microsoft.com/en-us/windows/win32/ktm/kernel-transaction-manager-portal).

Create a short local transaction with a bounded timeout and noninherited handle. `IsolationLevel` and `IsolationFlags` are reserved and must be zero; do not advertise a selectable serializable mode. Closing its final handle before commit rolls the transaction back. [CreateTransaction](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-createtransaction).

Open each participating key with the transaction, compare the fresh raw snapshot, and mutate through those handles. Microsoft documents rollback if a nontransacted operation interferes with a participating key. This is not a contract that every race returns the same code or that an external installer participates in the transaction. Revalidate provider absence immediately before commit; an MSI/package query and a registry transaction do not form one atomic installation-state decision. [RegOpenKeyTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeytransactedw).

For selected values, use `RegDeleteValueW` on the verified transacted key handle. For a leaf key, use `RegDeleteKeyTransactedW` with the verified parent, explicit view, and transaction. A key delete requires no child keys. Recursive transactional deletion is documented through `RegDeleteTree` with a transacted handle, but it still needs a complete reviewed tree and link checks; an arbitrary root is not an execution allowlist. [RegDeleteValueW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regdeletevaluew), [RegDeleteKeyTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regdeletekeytransactedw).

`RegDeleteTree(handle, NULL)` deletes that key's contents, not the key itself. It needs delete/enumerate/query rights, plus set-value rights when values exist. Do not count an emptied but retained key as a deleted key. Close all owned key handles deliberately and verify the final state with fresh handles. [RegDeleteTreeW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regdeletetreew).

Check `CommitTransaction` itself. Staging success is insufficient. Preserve the BOOL result, immediate last error, and transaction outcome where obtainable. `RollbackTransaction` is synchronous; check its result too. [CommitTransaction](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-committransaction), [RollbackTransaction](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-rollbacktransaction), [GetTransactionInformation](https://learn.microsoft.com/en-us/windows/win32/api/ktmw32/nf-ktmw32-gettransactioninformation).

Relevant errors include transaction-not-active `6701`, already-aborted `6704`, initialization-failed `6706`, conflict `6800`, and inactive resource manager `6801`. The system definition of `6800` concerns a name reserved by another transaction. Do not assert that all ordinary concurrent writes must yield `6800`. Keep registry `LSTATUS`, KTM last-error, and any native `NTSTATUS` distinct. [System error definitions](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--6000-8199-).

Change notifications can invalidate a preview promptly. They are not a lock: notifications are one-shot, handle/thread closure can signal them, and `RegRestoreKey` changes are not detected. A quiet watcher cannot replace a transaction-time snapshot. [RegNotifyChangeKeyValue](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regnotifychangekeyvalue).

## Retained-key quarantine

`RegRenameKey(verifiedHandle, NULL, uniqueSiblingName)` addresses the opened source key directly and can rename a whole subtree. It requires `KEY_WRITE`, creation rights on the parent, and delete rights throughout that subtree. The new name must be unused. This makes rename a useful candidate for reversible in-place quarantine. [RegRenameKey](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regrenamekey).

A rename avoids reconstructing the key's values and unknown creation metadata. Preservation of its underlying object is a reasonable implementation inference, but the API page does not expressly guarantee fidelity for every security/persistence/timestamp field. Quarantine also leaves data in the live registry under another name; it is not deletion, a space-reclamation claim, or a durable external backup. A volatile key can still disappear when its hive unloads. Retained external handles and concurrent writers require their own checks.

The published rename contract does not define transaction participation, isolation, or rollback. The lack of a transaction argument alone does not prove it is nontransacted: other registry APIs operate through transacted handles. Conversely, a successful rename does not prove rollback. Do not combine rename with a transaction receipt and claim atomic recovery until a fixture demonstrates that exact combination. The lower-level `NtRenameKey` documentation adds no transaction guarantee and warns that its interface may change. Prefer the documented `RegRenameKey` surface. [NtRenameKey](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntrenamekey).

If pursued, implement quarantine as a separate, explicitly named mode with durable intent, unique destination, verified post-rename name/data, conflict-safe rename-back, and a raw external backup. Never silently substitute it after a failed transactional delete. Do not write marker values into the quarantined key, since that would itself alter the retained content and timestamps. An existing original name on restore is a conflict. A changed quarantine snapshot is a conflict too; do not rename somebody else's replacement back.

**Implementation order:** ship the explicit persistent-recreation mode and existing value-only mode first. Probe quarantine independently; keep it separate until its actual rollback, concurrency, restart, and metadata behavior are known. Unsupported transactional rename need not prevent the supported delete/create transaction path.

## Native implementation sequence

1. Validate the review envelope, exact owner/provider identity, queue state, resource bounds, exclusions, and backup destination. Reject duplicate/ancestor-overlapping mutations after physical-view deduplication. Never accept an arbitrary registry root from the review as sufficient scope.
2. Scan with read-only native calls. Preserve every missing/inaccessible/incomplete result. Keep strong app-specific evidence separate from path/publisher-name suggestions. Present no unsupported candidate as executable.
3. Persist a canonical raw snapshot and its integrity digest outside the deletion scope. Flush and reread the backup before staging any delete. A digest protects integrity, not trust: bind it to the initiating operation and the caller's storage permissions.
4. Start the transaction, retain verified key handles, recheck their native names and complete approved snapshots, and stage only selected mutations. For multiple items, define one transaction per app review or another explicit bounded unit; report which unit can roll back atomically.
5. Persist commit intent before calling commit. A proposed recovery improvement is a small operation receipt in application-owned registry storage, written in the same transaction and bound to review/backup digests. This allows recovery to distinguish committed cleanup from an absent target created by another actor. Verify this cross-key behavior before depending on it; ordinary file writes are not automatically enlisted by KTM.
6. Commit, query outcome, and inspect resulting state through fresh handles. Report observed deletion, already-absent items, conflicts, and unknown outcomes separately. Never discard a valid backup because the final journal write failed.
7. Restore in a new transaction. Open and verify the existing parent; create one missing path component at a time with `RegCreateKeyTransactedW`, checking `REG_CREATED_NEW_KEY` versus `REG_OPENED_EXISTING_KEY`. Do not let its automatic multi-level creation fabricate missing scope. Existing conflicting state remains untouched. [RegCreateKeyTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeytransactedw).
8. Restore exact supported value bytes and covered security, compare through the same handles, commit, then verify independently. Repeated restore is a no-op only after complete equality and operation binding. An interrupted restore retains the same conflict rules.

This can provide working cleanup and recovery for ordinary owned values and supported keys without a system-wide registry cleaner. It cannot establish ownership from similarity, reverse a vendor uninstaller, serialize all installers, or recreate undocumented key metadata.

## Independent disposable fixtures

Construct fixtures independently of production defaults. Use a random owned HKCU test root and sibling sentinels; record their original raw state with a separate reader. Place backups in a random owned temporary directory. Use only disposable registrations and do not invoke installed vendor uninstallers.

| Case | Independent construction | Required assertion |
| --- | --- | --- |
| Basic value/key recovery | A leaf and a nested tree with fixed literal raw bytes; include unnamed, zero-byte binary, `REG_NONE`, both DWORD orders, QWORD, Unicode, literal `%TEMP%`, and multi-string | Preview changes nothing; apply removes exactly the selected resources; restore returns exact type/count/bytes and covered metadata. Sibling sentinels survive. |
| Unsupported representation | Independently inject a malformed string or unusual numeric type; preserve the injected bytes in the oracle | Detection retains the raw data and explicit unsupported state. No mutation occurs unless that precise restoration representation is supported and verified. |
| Missing default vs empty default | One key lacks an unnamed value; another has a zero-byte unnamed binary value | Output distinguishes missing from existing empty data; restore never invents an unnamed value. |
| Same text, different raw value | Keep rendered text constant while independently changing numeric type, terminators, or byte length | Old review fails for a raw-state mismatch; no incidental sibling delete. |
| Shared view aliases | Open one ordinary HKCU software key with each WOW64 flag | It is reviewed/executed once. No assertion that HKCU views are always distinct. |
| Distinct view keys | Under two disposable `HKCU\Software\Classes\CLSID\{fresh GUID}` view instances, write different marker bytes without an activation server | Only the selected physical view changes. If that host maps them differently, report the observed map and do not substitute a passing shared-key test. |
| Denied versus absent | Give an owned key a temporary deny-read ACE while retaining a recovery handle/rights; use a separately missing sibling | The first reports access failure, the second absence. Restore fixture ACLs in `finally` and verify all sentinels. |
| Security coverage | A fixture with explicit DACL/protection flags; a separate supported SACL case when the token has the actual privilege | Restored coverage is independently equal. Unavailable security capture cannot turn into an empty descriptor or false full-restore result. |
| Link at target/ancestor/descendant | A disposable registry link points to an outside sibling sentinel with intentionally identical value bytes | The real destination check rejects it; the sentinel remains identical. Include a barrier-controlled link substitution after preview and before the transacted open. |
| Key replacement | Delete/recreate the reviewed leaf between preview and apply; also replace an ancestor | Detected changed identity/freshness invalidates review. Retained handles must not write to a new object after a second pathname lookup. Record the identical-content replacement limit. |
| Concurrent ordinary writer | Independent process writes after the executor's transacted read but before commit, using explicit barriers | If the outside write succeeds, cleanup cannot report a successful deletion of that changed value. Record actual write/commit errors and final bytes. |
| Concurrent transaction | Two transactions stage conflicting updates; also test disjoint sibling operations | Conflict leaves one coherent committed result; no mixed partial tree or automatic nontransaction fallback. Do not assume one fixed conflict code across all interleavings. |
| Fresh install or incomplete detection | Start with a favorable removed queue entry, then independently vary registration-present, denied-query, pending-reboot, missing owner SID, and incomplete provider state | Every blocking row prevents cleanup even when primary removal status remains favorable. |
| Crash windows | Terminate a disposable executor before commit, after commit intent, and after commit but before file-journal completion | Uncommitted edits disappear; committed state reconciles through durable evidence; retry does not delete newly created data. |
| Restore conflict and retry | Recreate one deleted target with new bytes/children/security before restoring; retry a successful restore after editing it again | No overwrite in either conflict. A fully identical prior restore is a no-op with no new mutation count. |
| Backup/review binding | Alter backup bytes; exchange app IDs, native names, views, and operation receipts; remove one required field without filling defaults | Each invalid request fails before registry mutation. |
| Availability and resource failures | Fail transaction creation, timeout, commit, backup persistence, or complete enumeration independently | Exact failed stage and platform status are retained; no destructive fallback and no claimed recovery beyond the captured evidence. |
| Explicit persistent recreation | Independently create one volatile and one nonvolatile owned key with identical values/security, under a persistent parent; pass source persistence as unknown in both reviews | The policy is explicit, both restore with captured data/permissions and the deliberately chosen nonvolatile creation option, and neither result claims to have reproduced original persistence. A separate fixture oracle can attempt nonvolatile child creation in a transaction and roll it back: it succeeds below the persistent restored key, while the original volatile fixture yields `1021`. An omitted or changed policy invalidates review. |
| Persistent recreation under volatile parent | Independently create a volatile parent, then exercise the persistent restore request below it | Preserve the actual creation error and roll back; do not silently choose a different persistence mode. Where available, `ERROR_CHILD_MUST_BE_VOLATILE` is the precise platform explanation. [System error contract](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-). |
| Rename quarantine and transaction participation | Hold a verified source handle; rename via `lpSubKeyName=NULL` in one transaction that is rolled back and another that is committed; inspect old/new names from a separate reader before and after each outcome | Establish actual visibility and rollback behavior. Failure or immediate visibility means it cannot be advertised as the proposed isolated rename transaction. Check data, descriptors, class, and retained-handle behavior independently. |
| Quarantine conflicts and lifetime | Recreate the original name; replace or modify the quarantine key; collide with the chosen sibling name; terminate after rename intent; use known volatile and nonvolatile fixtures | No overwrite or blind rename-back. Reconcile actual names/data after a crash. Test volatility through the rollback-only child-creation oracle; actual unload/reload lifetime proof requires a disposable hive. Do not reboot an operator machine for this check. |

For critical checks, use a controlled mutation that disables native-name comparison, raw snapshot comparison, commit-result checking, or restore conflict handling. Its corresponding independent case must fail for the intended reason. Restore the production behavior before the final suite.
